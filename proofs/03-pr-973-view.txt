# Closes #881

The class JSDoc on `Clause`, `Contract`, and `TemplateInstance` tells readers to set template data by either calling `setData` or by calling a `parse` method that accepts natural language text. `TemplateInstance` exposes no such `parse` method, and neither does `Clause` or `Contract`. The sentence is a copy-paste of pre-TypeScript Cicero docs that was never cleaned up after the legacy parser was dropped, so anyone following the JSDoc hits a `TypeError`. The issue proposes two routes; this PR takes Option 2 (the documentation fix), which is the smallest change that stops the JSDoc from lying and leaves the parse/writing surface for a future, deliberate feature decision.

While I was in `contract.ts`, the class description also opens with "A Clause must be constructed..." for a `Contract` class ΓÇö a second cut-and-paste slip in the same block. I corrected the subject so the sentence reads "A Contract must be constructed..." That is still inside the scope of Option 2 and does not change any runtime behaviour.

### Changes

- `packages/cicero-core/src/clause.ts` ΓÇö drop the "or by calling the parse method and passing in natural language text that conforms to the template grammar" clause; keep the `setData` sentence.
- `packages/cicero-core/src/contract.ts` ΓÇö same clause removed, plus the `A Clause must be constructed` ΓåÆ `A Contract must be constructed` fix for the class's own subject.
- `packages/cicero-core/src/templateinstance.ts` ΓÇö same clause removed on the shared base class.

Three files, documentation-only, no runtime behaviour touched.

### Flags

- Documentation-only; no code paths change, no public API surface moves.
- The issue laid out two options. Option 1 (re-implement `parse()` / `generateText()`) is a product decision for the maintainers and the roadmap, not something to fold into a drive-by fix. This PR is strictly Option 2 and leaves that door open ΓÇö if you'd rather close #881 as "won't fix the docs until the feature is back," I'm happy to retarget or close this PR.
